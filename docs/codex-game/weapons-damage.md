# Weapons And Damage

Read this file before changing shooting, reload, projectile visuals, prediction, hit resolution, armor, damage, or reticle dispersion.

Current owner scripts:
- `Assets/Game/Scripts/Gameplay/Robots/WeaponReloadController.cs`
  - Owns ammo count, reload timer, reload HUD state, and fire gating.
  - Human owner path starts local prediction, while `ServerTryApproveOwnerShot` atomically validates ownership/reload/ammo, consumes one shell, and starts server reload.
  - Bot/server path uses `ServerTryFireAuthoritative`.
  - For the local owner, it passes `VehicleRuntimeStats.Faction` to `GunCrosshair` and drives the active reload circle plus Nova Syndicate `CrosshairType2` light-element alpha from the predicted reload timer, reconciled against the authoritative reload remainder when available. The circle resets immediately when a shot starts and smoothly fills toward the ready state; light-element alpha is `0` immediately after the predicted shot and reaches `1` when the weapon is ready.
- `Assets/Game/Scripts/Gameplay/Robots/NetworkWeaponShooter.cs`
  - Owns projectile fire, projectile visual spawning, dispersion, authoritative hit resolution, and network RPCs for shot visuals/results.
  - Resolves the physical aim point from the actual `muzzleTransform` origin. If a close-range aim sample is behind the muzzle because the barrel is inside a target, the shot uses the muzzle's forward direction; this is shared by prediction and server authority.
  - Builds the authoritative random shot direction from the shared `DispersionConeProjection` tangent-cone basis. Zoom changes only camera presentation; it never changes the physical dispersion angle or deterministic shot sample.
  - The local and server rings use the restored legacy UI formula from `GunDispersionGlobalSettings`, with the current zoom scalar supplied by `CameraController`.
  - The visible local ring and `AimStatus` use the synchronized server-authoritative dispersion value; the owner model is only a fallback before the first server value arrives. This keeps the visual narrowing and HUD progress on the same server timeline.
  - Owns the single human fire RPC. The server validates finite shot data, limits the client muzzle offset to 8 meters, requests ammo/reload approval, and only then creates the authoritative projectile.
  - Rejected owner shots cancel the predicted projectile and reconcile the local reload timer to the server value.
  - `ServerFireAuthoritative` is used by bots and other server-authoritative fire paths.
  - The owner shot-result `TargetRpc` writes `Miss`, `Penetrated`, or `No penetration` directly to the active `GunCrosshair` during manual control. Only while `VehicleInputController.IsAutonomous` is enabled, the two penetration results use the compact `〰〰〰` glyph; `Miss` remains explicit. The status remains visible until another shot result replaces it.
- `Assets/Game/Scripts/Gameplay/Robots/ServerHitResolver.cs`
  - Server-side raycast/hit resolution helper.
- `Assets/Game/Scripts/Gameplay/Robots/DamageService.cs`
  - Applies resolved damage to vehicle health.
- `Assets/Game/Scripts/Gameplay/Robots/VehicleHealth.cs`
  - Networked health state and death handling integration.
  - Raises `OnDamaged` on observers after authoritative damage is applied; the local HUD `DamageScreen` uses this event for the red hit indicator.
  - `VehicleHUD` consumes the same event for pooled floating damage text and applies the target's ally/enemy HP color without changing authoritative health behavior.
  - On a confirmed death, disables configured hit colliders immediately, sends the observer death event with the attacker's network object id, then despawns the spawned vehicle `NetworkObject` on the server. The client never decides the network object lifetime.
- `Assets/Game/Scripts/Gameplay/Robots/DeathLogic.cs`
  - Releases configured visual debris only from the client observer death event. A server-only instance does not detach or simulate any debris.
  - Detached client parts are unparented before the network vehicle is despawned, so they remain local dynamic physics objects after the dead root is destroyed and can be pushed by other client-side physics objects.
  - Disables the root tracked, suspension, walker, ground-alignment, and gun-recoil presentation controllers before detaching debris, preventing post-death transform writes against deactivated or detached renderers.
  - In Editor play mode only, scans the full multi-selection and clears it when any selected object belongs to the dying vehicle before hierarchy mutation, avoiding Unity SceneView selection-outline renderer assertions. Player builds contain no editor-selection code.
  - Every registered IA/NV robot prefab has one configured detachable visual per non-armor `MeshRenderer` object. Meshes below `Armor` remain editor-only and are excluded from the serialized death list. The list contains only valid mesh-renderer roots and has no null placeholder entries.
  - `detachableVisuals` separates each visual debris root, debris collider, rigidbody, and renderer from the colliders that receive gameplay hits.
 - Registers the serialized detachable visual renderers and mesh colliders during `Awake`, `OnEnable`, and `SetVehicleRoot`; impact-surface data therefore remains available even when a vehicle prefab omits `DeathLogic` from `VehicleRoot.rootAwareBehaviours`.
  - Fully empty `detachableVisuals` slots are ignored so prefab inspector capacity does not produce runtime errors; a slot with any assigned collider, rigidbody, renderer, mesh collider, or behaviour but no root still logs a configuration error.
  - Optional `behavioursToDisable` entries stop visual animation before a detached rigidbody becomes dynamic.
  - The legacy parallel debris arrays are empty on registered IA/NV robot prefabs; all death debris uses `detachableVisuals`.
- Detached client parts are registered with `MapScopedObjectRegistry` and remain physically/renderably present until map unload. The network root is destroyed immediately after the death observer event; client `DeathLogic` deliberately does not destroy already-detached parts during that root teardown, while map cleanup still owns their final destruction.
- `Assets/Game/Scripts/Gameplay/Robots/RobotDestructionParticleController.cs`
  - Focused client-side destruction presentation owner. It spawns the center `ExplosionMain` burst plus one random standard and one random free explosion, then attaches persistent `PartFire` instances to the mandatory first detached visual and up to three additional randomly selected detached visuals.
  - `DeathLogic` remains responsible for the death/debris lifecycle and passes the computed robot center and detached roots into this controller; the controller does not own health, network authority, physics detachment, or gameplay damage.
  - One-shot destruction effects use the existing bounded `ProjectileRuntimePool`; looping `PartFire` is parented to detached debris, keeps world scale `1,1,1`, and is explicitly destroyed after 30 seconds.
- `Assets/Game/Scripts/Gameplay/Robots/VehicleArmorController.cs`
  - Single root-level armor owner for a vehicle prefab.
  - `turretColliders` and `hullColliders` are the only armor-surface lists. `additionalVehicleColliders` registers non-armor hit surfaces with the vehicle root.
  - Registers every configured collider with `VehicleColliderRegistry`, including its explicit turret/hull zone, and owns line-of-sight armor sampling.
  - Base armor comes only from API runtime stats: `turretArmor` or `hullArmor` in `front/side/rear` order. A missing, malformed, zero, or negative directional value resolves to `1000 mm`.
  - `highlightArmorInPrefab` enables or disables the red Prefab Mode armor overlay for that vehicle.
- `Assets/Game/Scripts/Gameplay/Robots/VehicleColliderRegistry.cs`
  - Static runtime lookup from a configured collider to its vehicle root and optional centralized armor controller/zone.
  - Falls back to the nearest parent `VehicleRoot` for a hit collider that is physically part of a robot but was not included in `additionalVehicleColliders`; this keeps root resolution aligned with the prefab hierarchy without making client visuals authoritative.
  - Also indexes registered vehicle roots by FishNet `NetworkObject.ObjectId` so an authoritative impact RPC can attach its visual to the moving robot without scene-wide lookup.
  - Re-registers each networked `VehicleRoot` by its assigned `NetworkObject.ObjectId` at server/client start so authoritative impact RPCs resolve enemy roots instead of falling back to a world impact.
  - Merges the inspector-wired vehicle visibility and armor renderer lists per root so robot decals can target only the hit robot through URP rendering layers.
  - Stores inspector-wired visual `MeshCollider`/`Renderer` pairs for optional cosmetic surface correction, but live robot projectile hits do not scan those meshes or enable disabled death colliders. Robot hit selection accepts only the registered armor collider returned by the ray and attaches impact FX to that collider; the visual-surface resolver remains for explicitly configured non-robot proxy colliders.
  - Wraps the impact-surface lookup in `Projectile.ImpactSurface.Resolve` profiling so a runtime capture can separate this physics-side correction from particle playback.
  - Hit-freeze captures additionally expose `Projectile.ImpactFx.Play.<target>`, `Projectile.ImpactFx.Particles`, `Projectile.ImpactSurface.MeshCollider.Raycast`, and `Projectile.ImpactSurface.Physics.SyncTransforms`; the diagnostics HTTP server exposes `top/client`, `top/physics`, and `top/render` views for these scopes.
- `Assets/Game/Scripts/Gameplay/Projectiles/ImpactVisualSurface.cs`
  - Serialized adapter for non-robot proxy colliders. It registers one physics collider with its visible `MeshCollider` and `Renderer` references without scene-wide runtime searches.
  - The five `Concrete_fence_v1` prefabs use a disabled non-convex visual `MeshCollider` for this mapping, including `Concrete_fence_v1_wall_set_v2`.
- `Assets/Editor/Game/ArmorPrefabHighlighter.cs`
  - In Prefab Mode, draws the red overlay for active objects referenced by the root `VehicleArmorController` turret/hull arrays; an object disabled with `GameObject.SetActive(false)` is not highlighted.
  - Respects the prefab-owned `highlightArmorInPrefab` checkbox.
- `Assets/Game/Scripts/Gameplay/Robots/Shared/DispersionConeProjection.cs`
  - Shared tangent-cone direction builder used by shot randomization; reticle sizing remains owned by the restored legacy UI calculation.
- `Assets/Game/Scripts/Gameplay/Robots/GunDispersion.cs`

- `Assets/Game/Scripts/Gameplay/Robots/BallisticProjectileMath.cs`
  - Ballistic math helpers.
- `Assets/Game/Scripts/Gameplay/Projectiles/Projectile.cs`
  - Projectile visual/simulation component.
  - Owns separate `robotImpactFxPrefab` and `groundImpactFxPrefab` references and selects `ExplosionProjectileRobot` for a registered `VehicleRoot`; all non-robot hits select `ExplosionProjectileGround`.
  - Authoritative projectiles own hit callbacks and damage-resolution timing.
  - Client visual projectiles sweep against the configured hit mask while flying. A local collision immediately spawns cosmetic impact FX, stops the shell/tracer head, and waits for the authoritative result without applying damage.
  - A predicted impact keeps the exact registered armor collider returned by the ray and attaches FX to that collider transform, so only the struck armor zone is involved; non-armor robot/death colliders are ignored and static Map/world hits remain unparented.
  - Client projectiles retain their `shotId` while pooled references are tracked, preventing a late RPC from resolving a reused projectile instance.
  - Authoritative confirmation suppresses a duplicate impact when the predicted and server target object IDs match. If a target ID is unavailable, world impacts within 2 meters are treated as the same impact. A different target or farther point produces a corrective authoritative impact.
- `Assets/Game/Scripts/Gameplay/Projectiles/ProjectileRuntimePool.cs`
  - Runtime pooling for projectiles.
  - Rejects impact and muzzle FX configuration, prewarming, and spawning in a server-only process. Hosts retain client FX because they also run a local client.
  - Keeps impact FX bounded by the configured inactive-pool size: when all pooled impact FX are active, the oldest active instance is reused instead of instantiating an unbounded number of persistent decals.
  - Removes destroyed impact FX from the active ownership list and skips destroyed inactive entries before reuse, preventing a destroyed Unity object from reaching `PrepareForPoolRelease`.
  - Accepts an optional attachment parent and hit collider. Robot hits use the struck armor collider transform without a visual-mesh scan; static Map/world hits remain unparented. Impact and destruction FX use the client `ClientSettings.gameplayRuntime.particleCameraOffset` toward the gameplay camera; muzzle FX opt out. Particle-only effects map the supplied normal to local `+Z`, and every pooled FX root restores its prefab-authored world scale after reparenting.
  - Attached impact FX use a hidden runtime anchor under the resolved visual mesh. The anchor compensates the mesh transform's effective axis scales without changing the robot mesh, while the pooled FX root remains the single common parent for its particles and decals; this keeps both visuals moving with the mesh without inheriting destructive non-uniform scale.
  - Local projectile hits pass the actual `RaycastHit.collider` so a configured `ImpactVisualSurface` can correct the Halo; network-only RPC fallbacks have only point/normal data and use the configured signed offset when no collider is available.
  - Robot hits pass the registered target `VehicleRoot` into the pooled FX for rendering-layer ownership, while the visual attachment follows the resolved mesh transform. Map hits pass no target and continue using the default projector layer.
  - Maintains an independent bounded pool for each impact prefab, so robot-hit and ground-impact instances never share pooled child FX state.
- `Assets/Game/Scripts/Gameplay/Projectiles/PooledImpactFx.cs`
  - Owns one serialized `impactProfile` per prefab. It drives particle-only one-shot assets (`GunShoot` and destruction bursts) plus the authored projector-and-particle profiles (`ExplosionProjectileGround` and `ExplosionProjectileRobot`) through the same bounded lifecycle; profiles without projectors skip decal setup and release after their particle lifetime.
  - Owns the reusable hidden attachment anchor used by `ProjectileRuntimePool`. The anchor follows the resolved mesh parent, compensates inherited scale, and keeps the FX root's authored scale intact; pooling detaches and recycles the anchor without modifying the robot's mesh transforms.
  - Applies local impact camera shake through CFXR effects with the gameplay camera, distance falloff, the client camera-shake setting, and a runtime strength scale of `0.3` so pooled impact shake is 70% weaker than prefab-authored CFXR strength.
  - Owns the inspector-wired URP `DecalProjector` on the impact FX prefab. `PlayImpact` starts from the authoritative or predicted `hit.point`, projects along `-hit.normal`, randomizes roll around the surface normal, and applies the signed `impactDecalSurfaceOffset` to the decal, glow decal, halo, and impact FX root. A negative offset moves the effect inward from an outer proxy collider toward a deeper visual mesh; the regular `impactDecal` remains visible until its pooled instance is reused or the map unloads.
  - For robot targets, configures the projector, glow, halo, and impact root directly from the physics hit point and normal; it does not resolve registered visual meshes. For non-robot targets with `ImpactVisualSurface`, it still resolves the serialized visible mesh; unconfigured non-robot colliders retain the physics hit point.
  - Drives the paired `impactGlowDecal` projector with the same transform, size, target-only rendering-layer mask, and pool reset as the regular impact projector. Its configurable `impactGlowFadeDuration` uses unscaled smooth-step fading after the hit. `impactGlowStrength` is the shared non-negative multiplier for the crack and halo paths; `impactGlowDecalEmissionStrength` adds a crack-only multiplier. Each pooled FX instance clones the glow material, reads its source `Emission_Strength`, and applies both script multipliers before enabling the projector so URP's decal entity cache receives the current intensity. The runtime fade scales both the projector `fadeFactor` and the material emission value, because the URP forward-emissive decal pass does not reliably fade from `fadeFactor` alone.
  - The prefab also owns a disabled `Impact Glow Halo` `MeshRenderer` using `ImpactGlowHalo.mat` and the local `Textures/Glow.png` mask. `PooledImpactFx` places this quad on the same hit surface and exposes `impactGlowHaloStrength`, HDR `impactGlowHaloEmissionColor`, `impactGlowHaloBaseColor`, and `impactGlowHaloSizeMultiplier` in the same Inspector component. The script writes those values to the runtime material before enabling the halo, then fades/disables it with the glow projector. This halo is the actual broad Bloom source; `impactGlowHaloStrength` and the HDR emission color control its intensity, while the crack emission setting only affects thin detail.
  - `ImpactGlowDecal.shadergraph` is a Unity/URP Decal graph with a `Sample Texture 2D` node and a correctly serialized `ColorRGB` `Emission` block; each variant's `ImpactGlowDecal.mat` binds its local `Textures/Emossion.png` to `Base_Map`, which is multiplied by `Emission_Strength` and connected to the `Emission` block. Transparent pixels remain invisible and the colored crack pixels provide self-lit emission without a runtime light. The regular impact remains persistent while both glow layers fade.
  - Robot impacts acquire one temporary Decal Layer for the resolved visual part renderer when a mesh-collider/renderer pair is available; unmapped armor or fallback hits use the registered whole-robot renderer list. The target layers use bits `2-31`, and repeated impacts that target the same renderer set share their layer by reference count, so persistent decals do not consume a new layer for every shot while simultaneous turret and gun impacts remain isolated. Each renderer loses only the impact bit owned by that allocation on pool release or external destruction. World impacts use rendering-layer mask `2` (bit `1`); Map and legacy test-map renderers, including their shared `Environment` and `Props` prefab sources, keep that bit. `VehicleColliderRegistry.RegisterRenderers` removes only bit `1` from registered robot renderers at runtime, preserving the default lighting bit `0`, so a persistent ground/wall decal cannot project onto a robot that later enters its volume.
  - Notifies `ProjectileRuntimePool` when an instance is destroyed externally and ignores a destroyed component if a release race reaches `PrepareForPoolRelease`.
- `Assets/Game/Scripts/Gameplay/Projectiles/Projectile.cs`
- Performs one initial embedded-collider sweep before normal segment casts. It backtracks the query origin outside an overlapping registered armor or map-geometry collider while still ignoring the firing vehicle, so a projectile whose muzzle starts inside an enemy or a wall cannot pass through it. World blockers include `Default`, `Ground`, and `Obstacle` because imported map walls and fences use `Default`.
  - The ray accepts only a collider registered by `VehicleArmorController` as armor for robot hits. Active non-armor colliders under a `VehicleRoot` are ignored, and disabled death/destruction colliders are never re-enabled or queried; the nearest registered armor is compared with the nearest world blocker.
- `Assets/Game/Scripts/Gameplay/Robots/ProjectileVisualSpawner.cs`
  - Visual projectile spawning support, including selection of the robot-hit or ground-impact prefab from the resolved target.

Fire flow:
- Human fire input is owned by `VehicleInputController` and consumed by `WeaponReloadController` on the owner.
- Owner path uses client prediction plus server RPC validation.
- `NetworkWeaponShooter` triggers `VehicleGunRecoilController.PlayRecoil` with the predicted owner shot and with each observer shot RPC, so the firing robot visibly recoils for both the local player and remote clients without waiting for hit resolution.
- The owner sends one fire RPC through `NetworkWeaponShooter`; projectile creation and ammo/reload consumption cannot be approved independently.
- The predicted owner projectile uses client-only collision to hide visible wall/target overshoot while waiting for the server. Remote observer projectiles intentionally skip client collision so an early embedded-collision check cannot erase the shot before its first visible frame.
- Remote observer visuals start at the live muzzle without latency backdating. If the authoritative resolve RPC arrives before the fire RPC, `NetworkWeaponShooter` buffers the result; a confirmed hit is held for a short minimum visual flight before `Projectile` applies the impact. Owner prediction, server collision, reload, damage, HP, kill state, and shot-result HUD remain unchanged and authoritative where applicable.
- Authoritative simulation uses `Assets/Game/Content/Combat/Projectiles/ServerProjectile.prefab`, which contains only `Transform` and `Projectile`: no mesh, renderer, trail, particle system, collider, rigidbody, material, or explosion FX reference.
- `NetworkWeaponShooter` prepares the authoritative projectile pool only for the server phase. Client projectile, robot-hit, ground-impact, and muzzle-flash pools are prepared only from client visual paths.
- A matching authoritative hit completes the waiting visual without replaying the same impact. A divergent authoritative hit may add a correction impact. A server miss releases the waiting visual; an already-played cosmetic prediction is not rolled back.
- The authoritative projectile catches up by the elapsed client tick time, capped at 0.30 seconds, so server damage timing stays close to client projectile timing.
  - Server validates reload/ammo in `WeaponReloadController` before `NetworkWeaponShooter` creates the authoritative projectile.
- `Assets/Game/Scripts/UI/HUD/GunCrosshair.cs`
  - Presents the owner weapon state in `Client.unity/Canvas/GameplayHUD/GameplayHudContent`. It selects the matching `AmmoCountText`, `ReloadStatusText`, reload fill `Image`, `AimStatus`, and penetration-status bindings for the active faction; switching bindings forces the current cached ammo/reload state and last penetration result into the new UI target.
  - Smooths the active reload fill only while it advances toward the charge target; decreases are applied immediately so a new reload starts at the correct empty state.
  - Uses the serialized `GameplayHudContent` regular-HUD root and `SniperScopeOverlay` scope root when switching between regular and sniper presentation. Every forward zoom profile with `showReticle = true` selects the black scope overlay with the central reticle, not the ordinary dispersion ring; multiple flagged profiles are reachable by the wheel. There is no separate sniper zoom profile.
- Bot fire uses `WeaponReloadController.ServerTryFireAuthoritative` and then `NetworkWeaponShooter.ServerFireAuthoritative`.
- Bot aim is not client-only: `BotCombatInputWriter` sends yaw, pitch, aim point, and aim forward through `VehicleInputController.ServerSetExternalInput`; the server uses that state for turret/gun control while synchronized copies drive the owner/observer presentation. `NetworkWeaponShooter` builds bot shot direction from the current physical gun transform, and `BotAimController` waits for that same direction to align before firing. A successful bot hit therefore cannot depend on an invisible or unreached logical aim path.
  - `GunShoot` is the client muzzle effect. `NetworkWeaponShooter` computes the muzzle-to-target direction and spawns it with that vector mapped to local `+Z`; it does not receive the impact camera offset.
- `ExplosionProjectileGround` is the non-robot impact effect. `Projectile` and authoritative hit RPCs pass the normalized collision normal as local `+Z`, so a floor hit points upward and a wall hit points away from the wall.
  - `ExplosionProjectileRobot` is the robot-hit effect. It is spawned at the collision point with its authored root scale and follows the hit robot when the network path provides an attachment root; its restored decal projectors remain configured by `PooledImpactFx`.
  - Robot destruction presentation is separate from projectile impact presentation: `RobotDestructionParticleController` receives the death center and detached visual roots from `DeathLogic`, while all health/death authority remains in `VehicleHealth` and FishNet RPCs.
  - `RobotDestructionParticleController` starts one mandatory `ExplosionMain`, one random standard explosion, one random free explosion, and looping `PartFire` instances on detached parts. Each `PartFire` keeps world scale `1,1,1` and is destroyed after 30 seconds.
  - The impact projector is centered on the corrected surface point, with angle fade from `0` to `90` degrees; the active ground and robot profiles use their authored `0.6`-unit projection depth. Centering the volume prevents thin flat Map meshes from being clipped when the physics hit lies on the projection boundary. Proxy world objects that need exact visual alignment must add `ImpactVisualSurface` and wire their physics collider, visible non-convex `MeshCollider`, and renderers in the prefab; the resolver temporarily enables disabled visual colliders and restores their state. `impactDecalSurfaceOffset` remains the signed fallback for hits without a visual-surface mapping; set the relevant profile to a small negative value such as `-0.05` only for intentionally larger proxy colliders. Map scene renderers and the shared world prefab renderer sources use rendering-layer mask `3` so world decals use bit `1` without changing the default light bit.
- Static Map obstacles which use the same mesh for `MeshFilter`, `MeshRenderer`, and `MeshCollider` must keep `MeshCollider.Convex` disabled when they have no `Rigidbody`. `Assets/Game/Content/Map_v100_v200/Environment/Buildings/Industrial/Hangars/Hangar_v1/Hangar_v1_full.prefab` is configured this way (`m_Convex: 0`); a convex hull can sit outside recessed or concave visible surfaces, causing `Projectile` to receive an incorrect `RaycastHit.point` and placing both the projectile and `PooledImpactFx` on the wrong surface. Do not compensate this asset with `impactDecalSurfaceOffset`; use that offset only for intentionally larger proxy colliders.
- The impact FX root may remain camera-facing, but robot hits are parented with world position/rotation/scale preserved to the hit mesh/collider transform so the projector follows hull/turret movement. Static Map/world hits use the world-space projector with no attachment parent and remain world-static. Pool release always returns the root to the FX pool hierarchy and restores target renderer masks.
  - Both impact prefabs contain disabled projector and halo children for the regular impact, crack detail, and broad self-lit halo. There is no per-impact runtime light for robot hits. All projectile-local glow tuning is exposed on each prefab's `PooledImpactFx.impactProfile`: `impactGlowStrength`, `impactGlowHaloStrength`, HDR halo emission, halo base color/size, crack emission multiplier, decal size/depth, and fade duration. The script overrides runtime intensity/color settings on cloned materials. Global `Assets/DefaultVolumeProfile.asset` Bloom remains a camera-wide setting with the currently saved `threshold=0.9`, `intensity=0.65`, and `scatter=0.8`; it is intentionally not duplicated in `PooledImpactFx`. The regular impact remains visible while the bounded impact FX pool retains that instance; when the active limit is reached, the oldest impact is reset and reused. The client gameplay cameras in `VehicleTest`, `Client`, `Map`, and `Map2` must keep HDR and URP post-processing enabled; the `Client` Test Mode camera specifically owns an explicit `UniversalAdditionalCameraData` component in `Client.unity`, with the Default volume layer selected. Without that serialized camera component, projectile/tracer and impact emission renders without a Bloom halo.
- World impact projectors use mask `2` (bit `1`) while the URP decal renderer has decal-layer filtering enabled with `decalLayers: 255`; robot renderers retain light bit `0` and have only the world-decal bit removed. Target-only robot filtering is controlled by the configured per-target bits `2-7`; repeated hits on an identical renderer set reuse its active bit, and no runtime impact layer may exceed the project's valid URP mask `255`.
- The URP package decal shader used by `ImpactDecal.mat` must remain in `ProjectSettings/GraphicsSettings.asset` under `m_AlwaysIncludedShaders`; the Editor can resolve this package shader from `PackageCache`, while a Windows Player otherwise renders impact projectors magenta after shader stripping. Keep `m_StripUnusedVariants: 1` for normal project-wide stripping; `Assets/Editor/ImpactDecalShaderVariantStripper.cs` explicitly preserves only the required projector passes for the two impact decal shaders, avoiding the URP 17.3 bug that removed every DBuffer projector variant from the Windows Player.
- Damage should be applied only through authoritative server hit resolution, not directly from bot AI.
- Local damage feedback is client-side UI only: `VehicleHealth.OnDamaged` drives `DamageScreen` without affecting damage calculation.

T2 armor and destruction prefab contract:
- Registered Iron Alliance robot prefabs under `Assets/Game/Content/Robots/IronAlliance` register only colliders below objects named `Armor` as armor damage surfaces.
- Its single root `VehicleArmorController` contains six hull colliders and seven turret/gun colliders. `ChassisT2` is the one registry-only non-armor collider.
- `CabineReal`, `WeaponReal`, `MeshReal`, and wheel holders are transform/animation parents only. Each non-armor `MeshRenderer` child owns the matching disabled convex `MeshCollider` and kinematic `Rigidbody`, using that object's `MeshFilter.sharedMesh`. Armor mesh objects remain editor-only and keep their armor-controller collider setup.
- On death, all configured mesh-renderer objects detach, move recursively to the `Chassis` layer, enable their mesh colliders, and become non-kinematic. Wheel and body presentation behaviours are disabled before physics starts.
- `CaterpillarTrackLeft` and `CaterpillarTrackRight` remain visual-only and are deactivated on death instead of detaching.
- `VehicleClientVisibility` releases the death renderers from future spotting changes while preserving whether the vehicle was visible at the death moment. Visible debris stays visible until map unload; already-hidden enemies do not reveal debris.

T1 Hunter destruction prefab contract:
- Registered Nova Syndicate robot prefabs under `Assets/Game/Content/Robots/NovaSyndicate` currently use eight armor damage surfaces. The root armor controller assigns the three cubes below `Body` to its turret array and the central hull cube plus four leg-section cubes below `Chassis/ChassisMain` to its hull array.
- The root `VehicleArmorController` contains three turret/gun colliders and five hull/leg colliders. Child armor objects contain only Unity collider/renderer components.
- Their local position, rotation, and scale are authored independently. Adding or duplicating an armor cube requires adding its collider to the matching root armor array and the health collider list.
- On death, `DeathLogic` asks the centralized armor controller to disable all configured armor surfaces.
- The previous legacy debris arrays and parent-level rigidbodies/mesh colliders are removed. Each NV mesh-renderer object is directly assigned as a `DeathLogic.detachableVisuals` root and remains disabled physically until death.
- Death detaches and simulates each rendered mesh object, so every visual body/gun/turret/leg part uses its own mesh-aligned center of mass and collider shape.

Dispersion and aim:
- `NetworkWeaponShooter` updates server and owner dispersion in `Update`.
- Crosshair/HUD reads owner/server state through existing components.
- The local reticle may use the live point from an active `VehicleAutoAimController` for presentation only; projectile direction, fire validation, and dispersion calculations continue to use the weapon aim controller.
- Bots decide when to press fire based on line of fire, reload state, aim alignment, and the current `BotCombatTacticSelector` aim-readiness requirement; shot spread is still applied by weapon systems.
- `GunDispersionModel` now uses three runtime inputs for spread: horizontal vehicle speed, actual turret-local yaw speed, and recent shots.
- Vehicle speed contributes up to 50% of the weapon's `minDispersionDeg` to `maxDispersionDeg` range: 50% max speed = +25% spread, 100% max speed = +50% spread.
- Turret movement contributes proportionally up to 50% spread: actual `VehicleTurretRotationController.CurrentLocalYaw` speed is divided by `VehicleTurretRotationController.rotationSpeed`, with a small deadzone so very slow turret tracking stays at minimum spread.
- A shot adds a temporary +50% spread after the shot ray is built; it affects the next aiming state, not the already-fired projectile.
- The final target factor is `clamp01(vehicleSpeed01 * 0.5 + turretSpeed01 * 0.5 + shotDispersion01)`, then lerped between `minDispersionDeg` and `maxDispersionDeg`.
- Hull rotation, gun pitch motion, and camera aim motion no longer add dispersion.
- Max speed for normalization comes from `VehicleRoot.RuntimeStats.Speed` when available, otherwise `VehicleMovementController.maxSpeed`.

Rules when editing weapons:
- Do not bypass reload/ammo gating.
- Do not apply damage from client-only visuals.
- Do not create projectiles or impact FX with unmanaged runtime allocations if existing pools can be used.
- Preserve FishNet ownership rules for owner RPC fire requests.
- If bot fire behavior changes, update `ai-bots.md` too.
